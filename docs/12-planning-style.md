# 12 规划风格与学习原则

## 1. 风格定义

本项目采用：

> 实践牵引、理论回流、证据晋级、受控并行、循环治理。

它是一套工程学徒式训练系统，不是按视频章节推进的课程表，也不是让 AI 批量生成项目的速成方案。

## 2. 三项核心原则

### 实践为主

实践不是照抄 Demo，而是围绕一个可验证问题完成：

```text
定义问题
→ 独立尝试
→ 实现最小切片
→ 测试与调试
→ 解释原因
→ 修改约束
→ 交付与反馈
```

实践具有优先权，但不排斥理论。项目负责暴露问题、提供上下文和检验理解；理论负责解释、抽象和迁移。

实践不等于让零基础学习者无指导地硬解完整问题。L0能力可以从带解释示例和补全任务开始，但示例必须逐步淡出，并以独立重建和迁移结束。

### 进度记录与理论回顾

进度记录不以观看时长、代码行数和提交次数为核心，而记录：

- 交付了什么
- 哪项能力产生了可靠证据
- 哪些代码仍无法解释
- 哪些错误反复出现
- AI使用到什么等级
- 哪个理论需要复习或迁移
- 下一步最小动作是什么

理论回顾不是重看完整课程，而是从项目、Bug、架构决策和考核缺口回到对应原理，再通过解释、反例和陌生任务验证。

### 反复思考与迭代规划

规划允许反复调整，但每次调整必须经过：

```text
观察证据
→ 判断根因
→ 设计最小改动
→ 明确成功与回退条件
→ 试运行
→ 保留、调整或撤回
```

没有新证据时，不反复重写总体规划。迭代的目标是提高学习效果，不是追求规划看起来越来越复杂。

## 3. 三个相互嵌套的LOOP

### 能力LOOP

```text
实践问题 → 独立尝试 → 暴露缺口 → 理论解释
→ 最小练习 → 项目迁移 → 变式验证
```

### 证据LOOP

```text
产出 → 测试 → 解释 → 记录 → 间隔复测 → 更新能力等级
```

### 规划LOOP

```text
周/阶段数据 → 风险与根因 → 最小课程调整
→ 执行 → 对比结果 → 更新或停止治理
```

能力LOOP每天发生，证据LOOP按任务和周期发生，规划LOOP只在有足够证据时发生。

## 4. 实践与理论的关系

采用“实践提出问题，理论形成解释，复习促进迁移”的结构：

| 理论来源 | 触发方式 | 处理方法 | 结束证据 |
|---|---|---|---|
| 前置理论 | 新任务开始前发现依赖 | 最小必要学习 | 能完成入门变式 |
| Bug驱动理论 | 错误反复或只会试错 | 最小复现、原理、反例 | 能解释根因并补回归测试 |
| 架构理论 | 需要选择接口、数据或模块边界 | 比较方案和约束 | 能说明取舍并完成迁移 |
| 系统理论 | 知识碎片化、面试或阶段复盘 | 形成概念图和横向比较 | 能跨项目解释和应用 |

理论不能只留下摘抄。每项进入回顾账本的理论至少需要自己的解释、一个例子、一个反例或边界，以及项目中的使用点。

## 5. 最小记录制度

记录遵循“足够决策、尽量少写”。

### 每日

使用 [每日日志模板](../templates/daily-log.md)，只记录：

- 主交付物和证据
- 最大问题或理论缺口
- 最高AI等级
- 当前状态和下一步

### 每周

使用 [周复盘模板](../templates/weekly-review.md)，汇总：

- 主线结果和独立考核
- 并行是否失控
- 重复错误与理论回顾队列
- 风险、恢复和下周调整

### 阶段

- 更新能力矩阵
- 完成项目答辩和迁移任务
- 清理已经失效的证据
- 只对影响后续决策的内容做总结

完整聊天记录、长篇流水账和无决策用途的截图不属于必要进度证据。

## 6. 理论回顾机制

理论条目使用 [理论回顾账本模板](../templates/theory-review-ledger.md)。状态分为：

- 待理解：无法用自己的话说明
- 待应用：能够解释但没有独立使用
- 待迁移：在原场景成功，但陌生变式未验证
- 已掌握：能够解释、应用并通过迁移检查
- 待复测：已有证据过旧或后续使用暴露问题

建议在首次学习后尽快回忆，数日后做变式，并在后续项目中自然复现。具体间隔由课程包设置，不机械追求固定日期。

已经掌握的理论不反复抄写，只保留偶发抽查和项目复现。

## 7. 额外治理角度

### 独立性与迁移

防止“跟着教程会做，换需求就不会”。由无AI任务、陌生变式、现场修改和A0–A4记录治理。

### 用户与市场价值

防止作品只有技术没有用途。由用户问题、成功指标、代理反馈、岗位样本和项目迭代治理。

### 资料可信度与技术变化

防止AI幻觉、旧教程和框架追逐。由官方资料优先、核对日期、范围控制和替换原则治理。

### 质量、安全与生产意识

防止“能运行即完成”。由Definition of Done、测试、部署、评测、权限、隐私、成本和恢复机制治理。

### 可持续性与动机

防止高强度计划短期冲刺后崩溃。由有效时间、疲劳信号、可见成果、风险分级和降载恢复治理。

### 范围与注意力

防止同时学习太多。由课程范围、Must/Should/Stretch、1＋2并行和WIP上限治理。

这些角度已经有专项文档，不再各自增加新的日报和评分表。

## 8. 优先级判断

出现冲突时，倾向：

- 可验证产出高于被动输入
- 独立证据高于完成时长
- 完整小项目高于大量浅层Demo
- 底层能力高于短期框架熟练度
- 官方与运行证据高于AI断言
- 用户问题高于技术炫技
- 最小有效调整高于全面重写计划
- 可持续进步高于短期极限负荷

## 9. 反模式

- 为了实践而跳过所有原理
- 为了理论完整而迟迟不做项目
- 为了记录而制造复杂表格
- 为了迭代而每周改总体方向
- 为了AI加速而让AI完成核心思考
- 为了求职关键词而堆叠框架
- 为了项目数量而保留大量低质量Demo
- 为了并行而同时开启多条主线

## 10. 风格治理停止条件

当课程包能够明确回答以下问题时，风格治理已经足够：

1. 本轮实践交付什么？
2. 哪些理论由实践触发并需要回顾？
3. 用什么证据证明理解和迁移？
4. 记录如何影响下一轮决策？
5. 哪些内容明确不做？
6. 何时停止治理并回到执行？

当前规划已经具备这些答案。后续优化应来自真实执行数据，而不是继续扩充原则数量。
