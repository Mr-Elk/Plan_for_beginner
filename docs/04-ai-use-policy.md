# 04 AI 使用与考核规则

## 1. 原则

AI 在本项目中承担解释、陪练、审查、生成变式和提高反馈速度的角色。学习者必须保留独立建模、编码、调试和解释能力。

AI 输出默认是不可靠候选，需要通过官方资料、运行结果、测试和推理验证。

## 2. 辅助等级

| 等级 | 定义 | 示例 |
|---|---|---|
| A0 | 完全未使用 AI | 无 AI 周考、现场编程 |
| A1 | 概念解释或最小提示 | 解释报错术语、提出一个思考方向 |
| A2 | 方案或调试指导 | 比较两个设计、指出可能的 Bug 区域 |
| A3 | 生成局部代码 | 编写一个函数、测试样例或配置片段 |
| A4 | 生成大部分或完整实现 | 生成完整功能、页面或项目 |

每个学习任务记录实际使用过的最高等级，不按最初意图记录。

## 3. 求助前置条件

除概念预习和环境故障外，学习者向 AI 求助前必须提交：

- 自己对问题、输入、输出和约束的重述
- 预期结果与实际结果
- 伪代码、最小代码、失败测试或报错等首试产物
- 已经尝试的方法和当前具体卡点

没有首试产物时，AI应先引导学习者完成问题重述或最小尝试。首次求助默认从A1开始；只有再次尝试仍无进展时才升级。完整流程见 [高效学习步骤](13-efficient-learning-process.md)。

## 4. 场景规则

| 场景 | 允许等级 | 约束 |
|---|---:|---|
| 新概念预习 | A1–A2 | 必须回到主教材或官方资料核对 |
| 普通练习 | A0–A2 | 先完成有产物的独立首试，不以机械计时替代尝试质量 |
| 主项目设计 | A1–A2 | 学习者先提交自己的需求拆解和方案 |
| 主项目实现 | A1–A2为常态 | A3代码必须理解、测试并重写关键部分 |
| 代码审查 | A2–A3 | AI指出问题，学习者实施修改 |
| 测试设计 | A2–A3 | 不能只使用AI已见过的测试验收 |
| 研究优秀实现 | A4 | 只能作为阅读材料，不算个人成果 |
| 周考/阶段考核 | A0 | 禁止AI、搜索答案和查看现成实现 |
| 现场变式修改 | A0 | 允许使用语言/框架官方文档时需预先声明 |

## 5. A3/A4 后的恢复要求

如果使用 A3：

1. 逐行解释生成代码。
2. 补充至少一个 AI 未提供的边界测试。
3. 修改一个需求条件。
4. 在 24–72 小时内关闭 AI 重写关键部分。

如果使用 A4：

- 该实现不计入独立能力证据。
- 学习者需要重新设计一个相似但不同的任务。
- 新任务在 A0–A1 下完成后，才能恢复该能力证据。

如果辅导 AI 已经见过完整答案或隐藏测试，该 AI 可以继续教学，但不能独立确认本次考核通过；需要更换未污染的变式和验收上下文。

## 6. AI角色分离

同一个 AI 对话不应同时掌握题目答案、学生过程和最终评分的全部上下文。执行阶段至少逻辑分离：

- 课程设计者：依据路线图生成知识块和练习
- 苏格拉底教练：只给分级提示
- 代码审查者：检查代码、测试和风险
- 考核设计者：生成未见过的变式和评分标准
- 验收者：依据运行结果、隐藏测试和口头答辩评分

AI 的评分只能作为建议，最终结论必须包含确定性测试或人工可核查证据。

私有答案、隐藏测试和完整评分锚点必须位于学习者及其辅导 AI 无法访问的独立位置。把文件加入 `.gitignore` 只能防止提交，不能视为访问隔离。

## 7. 课程内容可信度

AI 生成课程包时必须：

- 明确学习目标和前置知识
- 指向主教材或官方资料
- 区分事实、经验建议和可选方案
- 提供可运行的最小示例
- 对版本敏感内容注明生成日期或核对日期
- 不虚构 API、参数、命令和来源

## 8. 安全与隐私

不得向 AI、公开仓库或课程材料提交：

- API Key、密码、Cookie、SSH私钥
- 云服务器密钥和完整生产配置
- 他人隐私数据
- 未获授权的公司代码或数据

所有项目必须使用环境变量、示例配置和脱敏数据。发现秘密进入 Git 后，除了删除文件，还必须立即轮换秘密。

## 9. 违规与证据失效

以下情况会使当前任务或项目证据失效：

- 隐瞒 A3/A4 使用
- 将完整 AI 生成项目声明为独立完成
- 无法解释核心代码仍拒绝重做
- 伪造 Git 过程、测试或学习时间
- 在无 AI 考核中使用模型或答案

失效用于纠正能力判断，不进行人格化惩罚。后续通过独立变式任务可以重新建立证据。
