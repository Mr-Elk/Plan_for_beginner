# 15 中文技术内容生成规范

## 1. 适用范围

本规范约束项目内由AI生成或改写的中文内容，包括阶段指南、周任务、课程包中的学习说明、知识讲解、项目案例、复盘反馈和面试解析。

控制表、证据索引和状态记录可以保留必要的工程术语，但只要内容直接面向学习者，就必须先让人看懂“为什么做、具体做什么、做到什么程度”，再出现编号、指标和治理信息。

写作目标不是模仿某位作者，也不是刻意使用网络口语。目标是采用中国技术文章常见的表达顺序：从实际问题进入，把背景交代清楚，沿着因果关系展开，用代码、数据或现实流程验证结论，最后说明适用边界和下一步。

## 2. 六项基本要求

### 2.1 内容详细

“详细”不是字数多，而是读者在需要行动或判断的地方，不必靠猜。

一段详细的技术内容至少要根据场景回答这些问题：

- 为什么现在要处理这个问题；
- 输入、输出和约束是什么；
- 先做哪一步，后做哪一步；
- 每一步为什么这样做；
- 正常情况和主要异常情况分别怎样处理；
- 怎样验证结果；
- 什么时候不适用，或者还有什么代价。

不影响理解、行动、验证和取舍的信息，不因为“显得全面”而加入。

### 2.2 文本简练

详细与简练不冲突。详细负责补足必要信息，简练负责删除重复信息。

- 一段只推进一个主要意思。
- 能用一个准确动词说清楚，不使用三个近义词堆叠。
- 已经在表格或代码中表达的内容，正文不再逐项复述。
- 不连续使用“首先、其次、再次、最后”填充节奏；只有顺序真实存在时才编号。
- 不用总结段重复整篇内容，只保留结论、边界和下一步。

### 2.3 描述精确

技术描述尽量包含明确的主体、动作、条件和结果。

不要只写：

> 深入理解数据库事务，建立可靠的数据处理闭环。

应写成：

> 在“创建订单并扣减库存”的操作中，让两次数据库修改要么全部成功，要么全部回滚。然后故意制造库存更新失败，检查订单是否留下了半成品数据。

以下词语不能单独作为学习目标：了解、熟悉、掌握、深入、提升、优化、赋能、沉淀、闭环。使用时必须补充可观察行为，例如“能够写出”“能够解释”“能够复现”“能够比较”“能够在新约束下修改”。

版本、环境、时间限制、允许工具、数据来源和不确定性会影响结论时，必须明确写出。事实、经验判断、教学假设和待验证内容要分开表达。

### 2.4 需要讲解时可以写长，但必须逐层展开

复杂概念不能为了简短压成几句口号。需要长篇解释时，默认沿着下面的顺序展开：

```text
读者正在遇到的问题
→ 先给结论和整体图景
→ 解释关键对象和它们的关系
→ 按一次真实流程逐步运行
→ 展示正常结果
→ 展示一个失败或反例
→ 解释边界和替代方案
→ 回到当前项目给出下一步
```

长文必须有清楚的因果连接。每引入一个新概念，都要说明它解决了前文的哪个问题。不要突然跳到更高层术语，也不要把二十个并列要点当作“系统讲解”。

如果读者只看开头两段，应能知道结论和阅读价值；继续阅读时，才能逐步获得原理、案例和边界。

### 2.5 使用现实案例贯穿阶段和项目

讲一个阶段或完整项目时，优先选择现实中确实存在的业务流程，不使用“任务管理器”“天气Demo”之类无法承载后续工程问题的占位案例。

默认贯穿案例可以使用“小型电商售后与知识库助手”：

| 阶段 | 现实工作中的变化 | 技术学习对应物 |
|---|---|---|
| P0 | 整理几份售后文本，尝试自动提取问题类型 | 文件、命令行、Python起点、模型调用 |
| P1 | 做一个本地售后工单工具，能够保存、查询和分类 | 函数、模块、异常、SQLite、测试 |
| P2 | 让客服系统通过接口创建和查询工单 | HTTP、FastAPI、PostgreSQL、认证和权限 |
| P3 | 客服人员通过网页登录、搜索和处理工单 | React、端到端流程、部署、日志和反馈 |
| P4 | 比较规则、机器学习和大模型的工单分类效果 | 数据质量、基线、指标、泄漏和错误分析 |
| P5 | 客服回答前检索商品手册，或经确认后更新工单 | RAG、引用、工具调用、状态和评测 |
| P6 | 控制错误回答、超时、费用、越权和提示注入 | 观测、恢复、安全、成本和版本对比 |
| P7 | 把系统整理成可演示、可答辩的求职项目 | 作品集、外部评审、面试和真实投递 |

这个案例是解释工具，不是强制选题。阶段合同可以改成招聘、教育、企业资料、内容审核或其他真实业务，但必须保留完整角色、数据流、异常和验证方法。

### 2.6 区分“现实案例”和“类比”

现实案例描述系统真正处理的业务，例如客服创建工单、查询手册和更新状态。类比只是帮助理解抽象概念，例如把API比作服务窗口。

使用类比时必须说明对应关系和边界：

- API像服务窗口，因为调用者只需要按约定提交材料，不需要进入内部处理区；但API还包含机器可校验的数据格式、状态码和权限，不能只靠口头约定。
- 数据库事务像银行转账，因为扣款和入账不能只完成一半；但数据库事务的隔离级别、锁和失败恢复需要进一步用实际代码说明。
- 消息队列像取号排队，因为生产者和处理者可以按顺序解耦；但重复消息、消费失败和顺序保证不能靠类比解决。

类比用于建立第一幅图，代码、运行结果和边界用于形成真正理解。不要使用幼稚化、夸张或与技术机制不一致的类比。

## 3. 符合中文技术阅读习惯的展开方式

### 3.1 从问题进入，不从定义大全进入

中国技术文章常见且有效的开头，是先说明实际遇到了什么问题，再引出需要的概念。

不推荐：

> 本节将系统介绍HTTP、REST、状态码、JSON和接口设计的相关知识。

推荐：

> 目前这个工具只能在自己的电脑上运行。下一步要让网页和其他程序也能使用它，因此需要先约定：请求发到哪里、携带什么数据、成功和失败分别返回什么。HTTP接口就是这套约定的载体。

### 3.2 多用动作和因果，少用抽象名词串联

不推荐：

> 完成模型能力接入与结构化输出契约建设，实现异常场景下的可靠性保障。

推荐：

> 让模型只返回约定好的JSON字段。程序收到结果后先校验字段和类型；如果格式不对，就记录原始响应并走失败处理，不能直接把错误数据写入数据库。

句子中连续出现三个以上“的”或多个名词时，应检查能否改成明确动作。

### 3.3 术语第一次出现时就地解释

- 优先使用行业中通行的中文名称；英文原词有助于查资料时，在首次出现处写在括号里。
- 缩写第一次出现时解释全称和当前用途，之后再使用缩写。
- 不单独建立庞大的术语表，让读者来回跳转。
- 同一个概念全文使用同一种叫法，不随意在“鉴权、认证、登录校验”之间切换。

### 3.4 保持自然语气，不制造虚假对话感

可以直接使用“你”说明学习动作，但不要连续使用“让我们”“显然”“大家都知道”“相信你已经理解”。不知道读者是否理解时，就给检查方法。

不要为了亲切大量使用感叹号、网络梗和夸张词。技术文章的可信感来自问题真实、解释清楚、例子能跑，而不是语气热闹。

## 4. 不同内容的默认写法

### 4.1 阶段指南

阶段指南优先回答：

1. 这一阶段结束后，现实中的项目多了什么能力；
2. 为什么现在做这些，而不是提前学后面的框架；
3. 主项目会按什么自然顺序成长；
4. 遇到问题时补哪些知识；
5. 哪些内容并行维护，但不能抢占主线；
6. 学习者根据什么现象判断可以结束阶段。

不要把控制表改写成散文。任务ID、门条款、审批状态和证据编号留在`stage-control.md`。

### 4.2 周任务和课程包

周任务先写本周唯一主结果，再说明背景和任务顺序。每项任务应包含可观察产物、主要失败情况和检查方法。

不要写“学习FastAPI基础”“掌握SQL”。应写“为创建工单增加POST接口，并为缺少标题、未登录和重复提交补上返回结果与测试”。

一周内容很多时，区分主线、随项目补充的基础和轻量回顾，不把三个槽位写成三门同时开课的课程。

### 4.3 技术原理讲解

先用当前项目中的一次调用或一次错误建立问题，再画出对象之间的关系。随后沿数据流或时间顺序解释，不按百科目录罗列定义。

讲完正常路径后，至少补一个失败案例或反例。最后回答“当前项目该怎样选”，避免只留下通用知识。

### 4.4 代码示例

- 示例代码只包含当前概念需要的结构，避免为了显得工程化加入无关封装。
- 代码前说明输入、预期输出和运行环境。
- 代码后解释关键行、运行结果和一个修改任务。
- 不能验证的伪代码明确标注为伪代码。
- 版本敏感的库用法必须核对官方资料和版本。

### 4.5 复盘和反馈

先写实际发生了什么，再解释原因。评价代码时指出具体文件、函数、输入或错误，不评价人格和“天赋”。

建议必须能转成下一步动作，并说明怎样验证修改有效。不要只写“加强基础”“注意规范”“继续优化”。

## 5. 防止AI味和翻译腔

出现以下信号时应重写：

- 每个阶段或章节都使用完全相同的标题数量和句式；
- 为了整齐，强行把内容拆成固定数量的并列要点；
- 高频使用“围绕、聚焦、赋能、构建、打造、沉淀、闭环、抓手、体系化”；
- 高频使用“不是……而是……”“既要……又要……”“通过……来实现……”；
- 段落里只有抽象名词，没有人、程序、数据和动作；
- 用“全面、深入、高质量、生产级”形容结果，却没有条件或检查方法；
- 开头反复出现“在当今快速发展的时代”“随着技术不断演进”“首先需要明确的是”；
- 结尾只是换一种说法重复前文；
- 案例名称真实，但数据、反馈和业务结果是编造的。

统一结构只用于帮助查找信息，不能让八个阶段读起来像同一段文字替换了名词。不同阶段应按真实学习难点选择篇幅和展开方式。

## 6. 生成流程

生成一份学习内容前，按下面顺序工作：

1. 确认读者是谁：学习者、负责人还是验收者。
2. 确认读者看完后要采取什么动作或做什么判断。
3. 找到一个真实问题；需要贯穿解释时，选择一个能承载完整数据流的现实案例。
4. 先写结论和主线，再决定哪些地方需要详细展开。
5. 为关键步骤补输入、输出、异常和验证方法。
6. 删除重复结论、空泛形容词、翻译腔和对称填充。
7. 检查术语、环境、版本、事实与假设。
8. 让目标读者试读；真实的不理解优先于写作者对“已经很清楚”的判断。

## 7. 发布前检查

面向学习者的内容发布前，应逐项确认：

- [ ] 开头两段能说明现实问题、阶段结果或本次任务。
- [ ] 读者知道下一步具体做什么，而不是只知道要学习哪个主题。
- [ ] 必要细节包含条件、过程、异常和验证，没有靠字数制造“详细”。
- [ ] 句子尽量使用明确主体和动作，没有连续抽象名词。
- [ ] 术语在第一次出现时得到解释，后续叫法一致。
- [ ] 长篇解释沿问题、机制、案例、失败和边界逐层展开。
- [ ] 案例来自可信的现实流程，没有编造用户、数据、收入和运行结果。
- [ ] 类比说明了对应关系和局限，并回到代码或实际行为。
- [ ] 重要结论能够通过代码、测试、文档或明确推理验证。
- [ ] 没有为了整齐强行复制其他章节的结构。
- [ ] 学习者内容没有泄漏不必要的任务ID、门条款和治理术语。
- [ ] 删除任意一段后若不影响理解或行动，该段已经删除或降为补充材料。

## 8. 与其他规范的关系

- 学什么、学到什么程度，由[课程范围地图](10-curriculum-scope.md)和[能力矩阵](02-capability-matrix.md)决定。
- 内容怎样组织成学习过程，由[高效学习步骤](13-efficient-learning-process.md)决定。
- AI可以提供什么程度的帮助，由[AI使用与考核规则](04-ai-use-policy.md)决定。
- 本文件只规定这些内容怎样用自然、精确、可行动的中文呈现，不降低原有能力和证据要求。
