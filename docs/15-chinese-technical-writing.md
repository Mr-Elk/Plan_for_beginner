# 15 中文技术写作规范

目标是让新手看完能行动，让负责人能验收。详细、简练和准确不冲突：关键推理写清，重复规则删掉，事实和边界写准。

## 1. 基本要求

1. 先写结论、目标或动作，再解释原因。
2. 一个段落只讲一个意思；一句话尽量只保留一层转折。
3. 使用常见中文表达，不直译英文句式，不堆“赋能、闭环、抓手、体系化”等空词。
4. 术语首次出现时用一句人话说明，后文保持同一名称。
5. 命令、路径、版本、输入输出、验收和非目标必须明确。
6. 不用“了解、熟悉、掌握、做好”作为任务结果，改成可观察动作。

例如：

- 差：掌握 FastAPI 的基本使用。
- 好：从空目录创建一个接口；输入缺少订单号时返回 422；为正常和失败请求各写一个测试。

## 2. 什么时候写长

只有概念难、因果链长、容易误用或关系到安全和方案选择时才展开。长文按下面顺序写：

```text
问题是什么
→ 为什么会发生
→ 最小例子
→ 怎样处理
→ 常见错误和边界
→ 怎样验证
```

背景介绍、重复提醒和文件职责不值得写成长文。能用一张表说清的比较，不拆成多个相同结构的小节。

## 3. 现实案例与类比

默认案例是“小型电商售后与知识助手”。阶段材料优先说明它怎样从 CLI 成长为 API、Web、检索或工具系统，再映射知识点。

| 阶段 | 案例增量 |
|---|---|
| P0 | 整理一段售后文本并调用一次模型 |
| P1 | 保存、查询和结构化工单 |
| P2 | 加入用户、数据库和 API |
| P3 | 客服通过网页完成核心流程 |
| P4 | 建立工单分类或优先级模型 |
| P5 | 检索售后规则或执行受控工具 |
| P6 | 加入评测、观测、回退、安全和成本 |
| P7 | 收敛为旗舰项目和求职证据 |

案例必须保留真实约束、失败和取舍，不能只换业务名。类比可以解释抽象概念，但类比之后必须回到准确定义、代码或数据验证。

## 4. 不同文件怎样写

| 文件 | 写什么 | 不写什么 |
|---|---|---|
| 学习者指南 | 本阶段做成什么、先后动作、完成信号 | 任务 ID、治理术语、长知识清单 |
| 控制表 | 任务、依赖、产物、门映射 | 教程式解释 |
| 课程包 | 当前两周结果、材料、练习、验收 | 复制总体规则 |
| 学习讲解 | 问题、例子、推理、错误和练习 | 大段正确但无法行动的背景 |
| 复盘 | 事实、证据、原因和决定 | 流水账和情绪化结论 |

## 5. 生成与审校

生成前先确认受众、唯一问题、所需动作、事实来源和非目标。初稿完成后按以下顺序删改：

1. 删除与本文件职责无关的内容。
2. 删除其他文件已有的规则，改成链接。
3. 合并重复段落和同构清单。
4. 把抽象动词改成可观察结果。
5. 检查案例是否真的改变了输入、规则和失败场景。
6. 检查命令、术语、编号和链接。
7. 让目标读者试读；记录看不懂和无法行动的位置。

## 6. 禁止的常见写法

- 每节都用“目标—原则—流程—产出—停止条件”的模板腔。
- 先写宏大背景，最后才说要做什么。
- 同一个规则在入口、路线图、模板和阶段文件重复出现。
- 为显得完整，把候选技术都列进当前任务。
- 只写正常流程，不写错误、权限、费用和数据边界。
- 用漂亮比喻代替准确解释。
- 连续使用括号、斜杠和英文缩写，让新手自己猜关系。

判断一段文字是否合格，只问三件事：读者知道下一步做什么吗，能判断做对了吗，删掉后会损失必要信息吗。
