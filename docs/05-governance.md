# 05 治理与变更控制

## 1. 治理目标

治理用于防止以下问题：

- 路线频繁变化导致无法积累
- AI不断增加新框架和新知识点
- 学习时间很多但没有能力证据
- 课程设计者、辅导者和评分者相互循环确认错误
- 因短期情绪推翻长期目标

## 2. 角色与责任

### 学习者

- 执行课程包并如实记录 AI 帮助
- 提交代码、测试、解释和复盘证据
- 及时报告卡点、疲劳和理解问题
- 对最终提交的代码承担理解责任

### 负责人/陪练者

- 批准项目章程和重大变更
- 检查周复盘、演示和阶段证据
- 保管独立考核材料或确保答案隔离
- 关注学习可持续性，不替学习者完成任务
- 借助 AI 工作时仍需依据治理规则验收输出

### AI助手

- 按指定角色和辅助等级工作
- 使用主教材与官方资料约束内容
- 制造案例、变式、测试和审查建议
- 不自行扩大项目范围
- 对不确定内容明确标注并请求验证

## 3. 决策权限

| 决策 | 谁可提出 | 谁批准 | 记录位置 |
|---|---|---|---|
| 每日任务顺序 | 学习者/AI | 学习者 | 当日日志 |
| 阶段指南或控制表细化 | 学习者/AI/负责人 | 负责人 | `stages/Px/README.md`、`stage-control.md`；重大影响进入CHANGELOG |
| S0正式开训 | 学习者/AI/负责人 | 学习者和负责人 | STATUS、P0阶段合同/课程包 |
| 阶段合同批准或修订 | 学习者/AI/负责人 | 负责人；改变总体门时还需学习者 | 阶段合同、必要时CHANGELOG |
| 两周课程包调整 | 学习者/AI/负责人 | 负责人 | 周复盘和课程包 |
| 阶段晋级 | AI建议/负责人 | 负责人依据证据 | 阶段报告 |
| 技术栈重大变化 | 任意角色 | 负责人 | CHANGELOG |
| 周期、方向、成功定义变化 | 任意角色 | 负责人和学习者共同确认 | 章程、CHANGELOG |
| AI考核边界变化 | 任意角色 | 负责人 | AI政策、CHANGELOG |

## 4. 资料优先级

课程内容来源按以下顺序选择：

1. 当前版本的官方文档和标准
2. 一个经过选择的主教材或系统课程
3. 项目源码、测试和运行行为
4. 高质量技术文章、论文或演讲
5. AI生成解释和示例

AI适合重组、解释和生成练习，不作为版本敏感事实的唯一来源。

## 5. 版本策略

- 项目章程和总体路线图使用 `v主版本.次版本`
- 改变目标、周期、岗位方向或成功定义：主版本增加
- 调整阶段顺序、周数或重要能力门槛：次版本增加
- 在既定路线和门内细化阶段任务：不自动提升总体版本；改变阶段结果、依赖或范围时按影响升级
- 阶段合同内部切片或课程包地图调整：不提升总体版本，在合同修订记录中说明
- 课程包内部调整：不提升总体规划版本，在周复盘记录
- 每次总体版本变化必须更新 `CHANGELOG.md` 和 `STATUS.md`

## 6. 变更流程

所有重大变更使用 [变更申请模板](../templates/change-request.md)：

1. 描述观察到的问题，不直接从喜欢的新工具出发。
2. 提供数据或证据，例如考核、岗位样本、项目阻塞。
3. 说明不变更的后果。
4. 给出至少一个低成本方案。
5. 评估对时间、范围、风险和现有课程包的影响。
6. 说明如何判断变更有效。
7. 设定回退条件。

禁止因为单次困难、单篇文章或单个新框架发布而立即改路线。

## 7. 评审节奏

### 每周

- 检查完成率、AI等级、无AI成绩、Bug类型和疲劳
- 只调整下一周任务，不修改总体方向

### 每两周

- 验收课程包
- 生成下一课程包
- 确定补修、正常或Stretch路径

### 每六周

- 检查阶段能力矩阵
- 更新风险和假设
- 允许提出阶段顺序或负载调整

### 每十二周

- 审查路线图是否仍服务目标岗位
- 抽样检查职位需求和技术生态
- 审查作品集质量和学习可持续性
- 必要时发布总体规划次版本

## 8. 范围控制

新增一个框架、平台或大型主题前，必须满足至少一项：

- 当前阶段闯关明确要求
- 主项目存在无法用现有技术合理解决的问题
- 多个目标岗位共同要求，且已有证据支持
- 能替换旧内容而不是只增加总量

如果只是“流行”“看起来高级”或“AI推荐”，默认不加入。

## 10. 三类待办隔离

为了防止想法直接污染当前课程，待办分为：

- 能力缺口：由考核和项目证据产生，优先进入下一课程包
- 项目待办：服务当前用户价值，按核心流程和非目标排序
- 技术候选：新框架、新工具和未来主题，只记录，不自动进入课程

技术候选只有满足“范围控制”条件并通过变更决策后，才能进入 Must 或 Should。

## 11. 治理预算

治理必须减少风险或提高决策质量，不能代替学习和交付。

- 执行开始后，常规治理维护原则上不超过有效训练投入的 5%
- 周复盘、证据链接和风险记录尽量复用现有产出，不重复抄写
- 没有新证据时，不因为想法更多而反复重写总体规划
- R3风险、重大方向变化或考核失效可以突破治理预算，但必须记录原因

## 12. 治理停止条件

一次总体治理LOOP满足以下条件时停止：

1. 目标、边界、角色和决策权明确。
2. 每个核心能力都有学习路径和有效证据。
3. 任务和项目有开始条件、完成条件和污染处理。
4. 高概率或高影响风险有早期信号、恢复动作和退出条件。
5. 文档之间没有关键冲突，课程包可以据此生成。
6. 剩余问题需要真实执行数据，而不是继续推理即可解决。

出现以下信号说明边际收益已经很小：

- 提议主要改变措辞、文件名或表格样式
- 新增检查项没有对应失败场景
- 新文档重复已有规则，却没有新的决策权或证据
- 为尚未发生且影响很小的情形设计复杂流程
- 治理复杂度增加得比风险下降更快

达到停止条件后，下一次总体治理必须由新证据触发，例如诊断结果、连续执行数据、考核失效、项目阻塞或岗位反馈。
