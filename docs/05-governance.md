# 05 治理与变更

## 1. 角色

| 角色 | 负责 | 不负责 |
|---|---|---|
| 学习者 | 实现、测试、解释、记录 AI 使用、报告负荷 | 自己宣布晋级 |
| 负责人 | 批准合同、控制范围、安排验收、保护私有材料 | 代写核心代码 |
| 课程设计 AI | 生成讲解、案例、练习和审查建议 | 持有私有答案、单独改变基线 |
| 验收者 | 执行独立检查、引用证据、给出结论 | 在考核中实时教学 |

一个人可以承担多个角色，但辅导与验收上下文必须分开。

## 2. 哪一层能改什么

| 变化 | 处理位置 | 是否改总体版本 |
|---|---|---|
| 当天顺序、练习数量 | 日志或周任务 | 否 |
| 课程包 Must/Should 调整 | 周复盘与课程包 | 否 |
| 阶段内任务取舍 | 阶段合同 | 否，需留修订记录 |
| 能力门、阶段顺序、总周数 | 总体文档 | 是 |
| 培养方向、成功标准、主要约束 | 项目章程 | 是 |

下层文件不能反向降低上层标准。发生冲突时依次看：章程、治理、能力与质量标准、阶段合同、课程包、周任务。

## 3. 变更流程

总体变更必须写清：

1. 哪条新证据触发变化；
2. 当前规则造成什么可观察问题；
3. 准备改什么、保持什么；
4. 对阶段、证据和执行产物有什么影响；
5. 怎样验证，失败时怎样回退。

使用[变更申请模板](../templates/change-request.md)。没有新证据，只是表达可以更清楚时，可直接做不改变语义的文档修订。

## 4. 评审节奏

- 每周：只处理交付、能力缺口和风险。
- 每两周：验收课程包，决定下一包。
- 每六周：看能力、负荷、AI 依赖和项目趋势。
- 每十二周或阶段边界：审查路线、岗位样本和重大假设。

执行开始后，常规治理原则上不超过有效训练时间的 5%。

## 6. 三类待办

- 能力缺口：由考核或项目失败产生，优先进入下一课程包。
- 项目待办：围绕当前用户流程排序。
- 技术候选：新框架、新工具和未来主题，只记录，不自动进入课程。

新内容只有在阻塞核心能力、多个岗位共同需要，或能替换现有内容时才能升级为必修。

## 7. 停止治理

当目标、角色、能力门、执行入口、证据和风险处理都明确，剩余问题只能靠真实训练数据回答时，应停止改总体规划，转入 P0。历史治理过程记录在 [09-governance-loop-log.md](09-governance-loop-log.md)。
