# 01 48周能力螺旋路线图

## 1. 路线图规则

- 48周和P0–P7提供推荐节奏与能力主攻窗口，不是八门串行课程。
- G0–G7是证据门；日历到期、看完资料或做出Demo都不自动触发晋级。
- 只有最低可观察依赖需要串行；一个能力可以提前进入L1，随后在项目中螺旋到L2/L3。
- 每两周只生成一个课程包，并围绕一个可演示的端到端纵向切片组织。
- 学习者从[阶段学习地图](../stages/README.md)进入；负责人进入每个阶段前再依据控制表和[阶段合同模板](../templates/stage-contract.md)筛选任务、映射能力门和批准执行范围。
- 同一时间只有一个主项目和一个主功能；多能力并行不等于多项目并行。
- 每六周进行一次周期复盘，必要时调整后续负载，不随意改变培养目标。
- 数据结构、算法、计算机基础、技术英语、测试、表达和AI纪律贯穿全年。

## 2. 一个交付现场，四条能力螺旋

```text
一个用户问题
  → 一个可运行纵向切片
      ├─ 交付螺旋：CLI → API → Web → AI产品 → 生产系统
      ├─ 基础螺旋：Python → HTTP/SQL → 系统基础 → 数据/模型判断
      ├─ AI螺旋：模型调用 → 结构化输出 → 工具/RAG → 评测与可靠性
      └─ 质量螺旋：Git/测试 → 部署/日志 → 安全/观测 → 用户与岗位反馈
```

四条螺旋是规划和复盘视图，不是四个并发任务。课程包仍按[受控并行执行模型](11-parallel-execution.md)运行：一条主交付流、一条基础支撑流和一条轻量巩固流。

同一能力使用“提前接触、当前主攻、后续加深”三种状态：

- 提前接触：建立目标感和基本模型，不作为当前阶段核心通过证据。
- 当前主攻：获得独立任务、项目迁移和阶段门要求的主要时间。
- 后续加深：在更复杂约束下复现，不重复从头学同一课程。

## 4. 各阶段的最小边界

### P0 开训诊断：第1–2周

主攻：验证环境、真实起点、AI纪律和40小时可执行性。

- WSL2、终端、目录、文件和权限基础
- Git提交、README、`uv`和项目环境
- Python变量、条件、循环、函数和基本容器
- 报错阅读、最小化复现和调试记录
- `.env`、`.gitignore`和密钥安全
- 一个普通CLI和一个最小模型调用CLI

最小产出：两个CLI、一次无AI基线考核、一份诊断报告。模型调用只用于建立完整链路，不证明AI工程能力。

### P1 可编程AI工具：第3–8周

主攻：能够独立把需求拆成函数、数据结构、模块和测试。

- 函数、作用域、模块、异常、文件、JSON和必要的类
- 类型标注、pytest、日志和调试
- 数组、哈希、栈、队列、链表、树、复杂度、排序、二分和遍历
- 使用模型API完成文本处理，并验证结构化输出
- 从JSON文件逐步进入SQLite或同等轻量持久化
- 用HTTP/JSON解释模型调用的数据流，不系统展开后端框架

项目：一个真实可用的Python工具，包含持久化、搜索、异常、测试、文档和一个受控AI功能。核心Python部分必须能够在A0–A1下重建。

### P2 AI后端切片：第9–16周

主攻：理解一次请求如何穿过接口、业务逻辑、数据库和模型服务。

- HTTP、JSON、REST和状态码
- SQL、表关系、索引和事务
- FastAPI、Pydantic、依赖、错误处理和集成测试
- PostgreSQL、迁移、配置、日志、认证和权限
- 结构化输出、最小工具调用或摘要链路
- 为AI功能建立小型固定样本、失败记录、延迟和费用字段
- 在接口稳定后，用极薄页面或API客户端完成真实调用

项目：带数据库、认证和AI功能的API服务；至少一个切片部署到Linux环境。G2仍以独立后端能力为核心，薄前端和AI预览不能掩盖HTTP、SQL或测试缺口。

### P3 可部署AI Web：第17–24周

主攻：把后端切片扩展成用户可以访问、反馈和维护的完整产品。

- HTML、CSS、JavaScript和React日常核心概念
- 文件上传、搜索、分页、流式响应和错误展示
- 登录、角色和权限边界
- Docker、Linux部署、反向代理、HTTPS概念和CI
- 结构化日志、基本监控、重试、限流、缓存和后台任务
- 选择一个受控的RAG或工具工作流作为产品能力
- 从第一个AI切片开始维护评测样本、失败案例和成本基线

项目：一个上线的AI Web系统。前端只服务核心用户流程，不展开前端专家路线；至少一名未参与实现的人仅依据README运行或使用并反馈问题。

### P4 数据与模型判断：第25–30周

主攻：完成数据到模型的闭环，并能判断何时不用LLM。

- NumPy、Pandas、清洗、数据质量和可视化
- 向量、矩阵、导数、概率和统计的即时复习
- 训练/验证/测试、数据泄漏、回归、分类和聚类边界
- 准确率、精确率、召回率、F1和混淆矩阵
- PyTorch张量、自动求导、训练循环和模型保存
- Token、Embedding、Attention和Transformer概念
- 对同一问题比较规则、传统ML和LLM方案

项目：一个有数据说明、基线、指标、错误分析和推理接口的ML应用。既有AI Web产品只做维护和小幅迭代，不能同时成为第二条大型主线。

### P5 智能工作流深化：第31–38周

主攻：在已具备后端和交付能力的基础上深入RAG与工具工作流。

- Prompt版本和输入输出契约
- 工具调用、参数校验、状态和人工确认
- 文档处理、切分、Embedding、召回、重排和引用
- 对话状态、有限记忆和失败恢复
- 不依赖复杂框架实现底层原型后，再按需要选择一个框架
- 本地模型推理体验与方案边界
- 检索、答案、延迟和成本的最小评测

项目：一个带引用的知识系统或一个带真实工具的工作流助手；另一个形态可以作为技能项目，不同时开启两个大型项目。

### P6 生产级AI：第39–44周

主攻：把“可用”升级为“可测试、可观测、可控制”。

- 离线评测、人工评测和版本对比
- 检索指标、答案正确性、引用和工具参数检查
- 超时、重试、回退、缓存和预算控制
- Tracing、Token、延迟和成本统计
- Prompt Injection、数据泄漏、工具权限和审计日志
- 人工确认、故障恢复和供应商变化下的稳定接口

项目：对P3或P5的主项目进行生产级重构，并提供前后评测对比、失败边界和恢复说明。

### P7 旗舰交付与求职：第45–48周

主攻：用一个完整工程和陌生任务证明综合能力。

- 在线演示、源码、自动测试和部署说明
- 架构图、数据流、威胁与失败边界
- 评测集、指标、成本和性能说明
- 演示视频、技术复盘和未来改进
- 简历、项目介绍、常见问答和模拟面试
- 真实投递反馈和针对性补强

## 5. 两周纵向切片合同

除诊断或阶段验收包外，每个两周课程包必须回答：

1. 本周期交付哪个唯一用户动作或系统能力？
2. 它至少穿过哪些层：业务逻辑、接口、数据、AI、界面、测试、部署？
3. 哪个基础缺口是当前支撑流，为什么现在补？
4. AI能力处于提前接触、当前主攻还是后续加深？
5. 本切片如何演示、独立重建、变式和收集反馈？
6. 哪些层明确不做，防止一个切片膨胀成多个项目？

推荐形态：

```text
一个用户动作
→ 一个接口或CLI入口
→ 一次数据处理/读写
→ 一个最小AI或规则能力（适用时）
→ 一组正常与失败测试
→ 一次可重复运行或部署验证
```

不是每个早期切片都必须包含所有层；缺失层必须是基于阶段能力和依赖的明确决定，而不是被永久推迟。

## 6. 贯穿式训练

### 内功维护

- 每周约4小时用于数据结构、算法和当前相关的计算机基础
- 全年参考100–140道精选题，重点是朴素方案、复杂度、变式和解释
- 后期减少孤立刷题，增加在缓存、检索、数据库和系统故障中的迁移

### 技术英语

- 每周约2小时，分散到多数训练日
- 阅读当前切片所需的官方文档、报错和Issue
- 允许翻译工具，但必须用中文复述结论并通过运行验证

### 求职与市场反馈

- 第8周：建立公开项目说明标准
- 第16周：收集并分析目标岗位样本
- 第24周：完成一次模拟企业任务或冷启动交接
- 第30周：根据岗位样本修订后半程优先级
- 第32周：开始项目讲解和模拟面试
- 第36周：少量真实投递并收集反馈
- 第40周后：持续投递并针对证据缺口补强

岗位样本只调整能力优先级，不直接把框架关键词变成必修课。

### 面试能力回顾

面试不是后期新增的一门课程，而是把已经学过的能力在限时、无完整上下文和需要清晰表达的条件下重新提取。面试训练复用独立考核、口头解释、故障诊断和项目答辩，不额外开启主线。

| 阶段 | 编码与基础 | 技术问答与诊断 | 项目、设计与沟通 |
|---|---|---|---|
| P0 | 基线小程序、读报错 | 终端、Git、Python执行过程 | 说明学习目标、首试和求助边界 |
| P1 | Python、容器、异常、基础算法 | 测试、复杂度、文件与模块 | 5–10分钟讲解工具的需求、设计和Bug |
| P2 | Python维护、SQL和后端变式 | HTTP、事务、索引、认证、接口故障 | 讲清一次请求的数据流和API取舍 |
| P3 | 端到端现场修改 | 权限、缓存、日志、部署和常见故障 | 完整项目讲解、冷启动交接和小型系统设计 |
| P4 | 数据处理或ML变式 | 指标、泄漏、过拟合、模型边界 | 比较规则、ML和LLM方案及失败案例 |
| P5 | 检索或工具链路修改 | Embedding、召回、RAG和工具失败模式 | 讲解AI工作流、评测设计和方案取舍 |
| P6 | 综合调试和陌生约束 | 评测、安全、可靠性、成本和观测 | 生产AI系统设计、事故复盘和权衡 |
| P7 | 混合限时任务 | 从历史核心域随机抽取 | 项目答辩、行为问题、模拟面试和真实反馈 |

执行节奏：

- 每周从当前主攻能力和历史回顾队列各做一次短主动提取；P0无历史项时只建立基线。
- 每两周课程包至少包含一次限时任务、一次口头/画图解释，以及一次与项目证据相连的回答。
- 每六周综合考核混合当前知识、历史核心知识和一个陌生迁移问题，不按章节顺序提示答案。
- P3以后逐步加入小型系统设计和未共享完整辅导上下文的模拟面试；P7再提高为完整流程。
- 回答失败先判断是知识缺口、提取失败、表达问题还是压力/时间问题；知识缺口进入理论账本，其余进入对应练习，不用背标准答案掩盖根因。

详细证据边界见[能力矩阵](02-capability-matrix.md)；具体题型和历史回顾项由两周课程包冻结。

### 协作与外部反馈

- P0–P1：通过Issue描述任务、PR提交改动并处理负责人意见
- P2–P3：让未参与实现的人仅依据README运行项目，学习者修复并回归
- P4–P6：让外部用户或开发者使用核心流程，对评测、接口或失败案例反馈
- P7：完成导师以外的人类代码评审、模拟面试或真实项目反馈闭环

AI评审可以提高频率，但不能作为人类协作能力的唯一证据。

## 7. 防止伪并行

出现以下情况时，立即降级为“主线＋复习”：

- 同时出现两个大型项目或两个正在实现的主功能
- 同一天从零学习两个复杂框架或抽象
- 活跃课程、分支和笔记增加，但端到端增量减少
- AI生成代码积压，尚未解释、测试或重写
- 为提前接触的新能力牺牲当前阶段核心门

恢复条件是：完成当前纵向切片、清理学习债务，并通过当前主攻能力的未污染变式。
