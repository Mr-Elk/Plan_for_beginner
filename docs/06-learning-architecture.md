# 06 学习架构

学习不是“先学完基础，再开始做项目”，也不是“只做项目，缺什么就全靠搜索”。本计划用项目暴露问题，再补能解释和解决问题的最小知识，最后用陌生任务验证迁移。

## 1. 四层结构

| 层 | 内容 | 怎样形成能力 |
|---|---|---|
| 交付层 | CLI、API、Web、AI 工作流、生产系统 | 完成一个用户能观察的结果 |
| 工程层 | Git、测试、日志、配置、部署、安全 | 让结果可重复、可维护、可恢复 |
| 基础层 | Python、算法、HTTP、SQL、系统、网络 | 解释行为并解决新问题 |
| 原理层 | 数学、机器学习、LLM、评测 | 判断方案边界和取舍 |

四层在同一个项目现场交汇，不分成四门同时推进的课程。

## 2. 学习闭环

```text
真实任务
→ 首次尝试
→ 暴露缺口
→ 补最小知识
→ 回到项目完成增量
→ 测试和解释
→ 陌生变式
→ 数日后复测
```

例如，售后 API 查询越来越慢：先复现慢查询，再学习索引和查询计划，修复后补性能对照，最后换一张表独立判断是否需要索引。只有“看完数据库索引章节”不算形成能力。

## 3. 知识依赖

只把无法绕开的前置条件设为串行：

```text
Python 基本控制流
→ 函数与容器
→ 模块、异常与测试
→ HTTP/SQL/FastAPI
→ 端到端 Web
→ RAG 或工具工作流
→ 生产可靠性
```

Git、调试、英语、算法和表达从一开始贯穿。数学在数据和模型任务出现时进入；不要求先完整重学三门大学数学。

## 4. 三种进入方式

- 项目先行：已经能开始任务，只缺局部知识。先做，再定点补。
- 知识先行：缺少最小前置，连问题都无法表述。先学一个可运行例子，再回项目。
- 诊断先行：不知道自己会不会。先做短任务，根据表现选择入口。

选择哪一种取决于当前任务，不给学习者贴“基础差”或“进度快”的长期标签。

## 5. 项目层级

| 层级 | 用途 | 典型时长 |
|---|---|---:|
| 微练习 | 验证一个语法、公式或 API | 10–40 分钟 |
| 技能任务 | 组合两三个知识点，做一次变式 | 1–4 小时 |
| 纵向切片 | 穿过业务、数据、测试和交付 | 2 周 |
| 阶段项目 | 汇总当前能力门的证据 | 4–8 周 |
| 旗舰项目 | 证明综合交付和外部反馈 | 跨阶段维护 |

低层任务服务高层项目；不能用大量微练习代替真实交付，也不能用 AI 拼出的完整项目掩盖基本能力。

## 6. 理论回流

出现以下情况时进入[理论回顾账本](../templates/theory-review-ledger.md)：同类错误反复出现、无法解释方案为何有效、面试提取失败、或新场景无法迁移。理论回顾必须留下自己的解释、例子、反例和项目使用点；抄定义不算完成。
