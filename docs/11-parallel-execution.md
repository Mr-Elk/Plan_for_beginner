# 11 受控并行执行模型

## 1. 结论

本项目允许并行，但不允许多个高负荷主线竞争注意力。推荐使用“1＋2”模型：

```text
1条主交付流：当前唯一主项目或核心功能
1条基础支撑流：算法、计算机基础、数学或当前前置能力
1条轻量巩固流：复习、英语、文档、代码阅读或错误回归
```

三条流不平均分配精力。主交付流占主导，支撑流必须服务长期基础或当前项目，巩固流使用低切换成本任务。

## 2. 为什么不能完全串行

完全学完一门再开始下一门，会产生：

- 基础知识长期没有项目迁移
- 算法、英语和计算机基础被挤到“以后”
- 直到后期才发现接口、部署或用户交付问题
- 学习反馈距离过长，降低动机

适度并行能让知识在不同场景重复出现，并利用等待、恢复和低精力时间。

## 3. 为什么不能无限并行

新手同时开启多个主线，会产生：

- 工作记忆被不同语言、框架和抽象争夺
- 每条线都停留在入门，无法形成完整证据
- 遇到困难时切换任务，形成“看起来很忙”的逃避
- AI为多个方向生成大量代码，独立能力更难判断
- 项目长期处于半完成状态

因此，并行优化的目标是提高反馈和利用率，不是增加同时学习的课程数量。

## 4. WIP限制

学习者同一时间最多保留：

- 1个主项目
- 1个正在实现的主功能
- 1个基础支撑单元
- 1个轻量巩固清单
- 1个有明确下一步的阻塞项

额外想法进入候选池，不直接开始。

以下情况必须先完成或关闭现有工作，不能再开新线：

- 主功能尚未形成端到端可运行切片
- 已有两个以上无法解释的核心知识缺口
- 出现未记录的环境或依赖阻塞
- A3/A4代码等待重写
- 周考或回归任务尚未处理

## 5. 依赖图

```text
Python L2 ───────────────→ 后端/API
   │                          │
   ├→ 数据处理 ─→ ML基础      ├→ 稳定接口 ─→ React界面
   │                          │
   └→ HTTP/JSON ─→ 模型API ───┤
                              ├→ 工具调用
SQL + 文本处理 + Embedding ──→ RAG

测试 + 日志 + 权限 + 部署
        └────────────────────→ 生产级AI
```

依赖图表示开始条件，不要求前置能力全部达到最高等级。通常达到 L2、能够独立完成常见任务后，即可让后续能力进入支撑流或主线。

## 6. 可以安全并行的内容

### 长期基础与主项目

- 主项目与数据结构/算法维护
- 主项目与技术英语、官方文档阅读
- 编码与Git、测试、日志、调试习惯
- 项目功能与对应的计算机基础解释
- 项目开发与间隔复习、错误回归

这些内容抽象不同、依赖低，而且能够相互强化。

### 后端与前端

可以流水线并行，但需要先稳定最小接口契约：

1. 先定义用户流程、请求和响应。
2. 后端交付一个可调用的垂直切片。
3. 前端围绕已稳定接口实现页面。
4. 后端继续下一切片时，前端完善上一切片。
5. 用端到端测试重新汇合。

学习者不应在同一天同时从零学习复杂后端概念和复杂React状态管理。

### 数学与机器学习

数学采用即时支撑：

- 学损失函数时复习函数、导数和梯度直觉
- 学向量和Embedding时复习向量、矩阵和相似度
- 学指标时复习概率、均值、方差和条件关系

不需要先完整重学三门数学，也不应完全跳过原理只调用库。

### LLM功能与质量工作

当最小AI链路已经可运行后，可以并行：

- 主线实现结构化输出、工具调用或RAG
- 支撑流制作评测样本、失败案例和安全用例
- 巩固流补文档、Tracing字段、成本记录和回归测试

评测和安全不能等功能全部结束才开始，但也不能在链路尚未定义时凭空设计复杂体系。

### 项目与职业准备

- 项目开发与README、架构讲解同步进行
- 完成一个功能后立即沉淀项目故事和失败案例
- 岗位样本可以校准能力优先级，但不打断当前主功能

## 7. 不适合并行的组合

| 组合 | 原因 | 替代方式 |
|---|---|---|
| Python基础 + Java/C++主课 | 语法和模型干扰，暂时没有收益 | 第一轮只用Python |
| 后端基础 + React深度课程 | 两套新抽象争夺注意力 | 后端形成接口后再做薄前端 |
| ML系统学习 + RAG/Agent主线 | 数据、模型和应用抽象同时过多 | ML作为独立主线后再进入LLM |
| 多个后端或Agent框架 | 学到的是API差异，不是底层能力 | 只保留一个主框架 |
| 两个大型项目 | 交付、测试和复盘都被稀释 | 一个主项目，另一个只能是微型练习 |
| 学习新概念 + 重构核心系统 | 难以判断问题来自知识还是设计 | 先用最小示例验证，再重构 |
| 无AI考核 + 辅导AI后台提示 | 破坏独立证据 | 考核上下文完全隔离 |

## 8. 各能力重点下的并行矩阵

| 当前主线 | 基础支撑流 | 轻量巩固流 | 暂缓 |
|---|---|---|---|
| Python项目 | 算法、Linux/Git | 英语、错题、README | React、ML、RAG主课 |
| 后端API | SQL、HTTP、算法维护 | 接口文档、测试回归 | 多后端框架、复杂前端 |
| 全栈交付 | 薄前端或部署（二选一为重点） | 端到端测试、用户反馈 | UI深度、微服务 |
| 数据/ML项目 | 即时数学、数据质量 | 指标复盘、推理API维护 | Agent、多模型框架 |
| LLM原型 | 评测样本、检索原理 | 失败集、成本与文档 | 微调和复杂多Agent同时开启 |
| 生产级AI | 安全、可靠性、观测 | 回归、项目讲解 | 新模型和新框架追逐 |
| 旗舰交付 | 面试变式、系统基础维护 | README、演示和复盘 | 新的大型项目 |

“薄前端”指只实现核心用户流程，不展开完整前端专家课程。

## 9. 垂直切片优先

主项目不按“数据库全部完成→后端全部完成→前端全部完成”组织，而按一个可用流程切片：

```text
一个用户动作
→ 一个接口
→ 一次数据读写
→ 一个最小界面
→ 一组测试
→ 一次部署验证
```

完成一个切片后再扩展下一个。这样前后端、测试和部署可以形成流水线，又不会出现多条未完成主线。

## 10. 学习者、负责人和AI的并行流水线

| 角色 | 当前单元 | 下一单元 | 禁止事项 |
|---|---|---|---|
| 学习者 | 独立尝试、实现、测试、解释 | 只查看已批准的预习目标 | 提前查看答案和隐藏测试 |
| 负责人 | 观察证据、演示抽查、管理风险 | 批准下一单元和私有考核 | 代替学习者写核心实现 |
| 课程设计AI | 回答已批准范围内的问题 | 最多提前准备一个课程包 | 无限生成未来课程和框架 |
| 辅导AI | 按A1–A2分级提示 | 不接触下一次私有答案 | 同时担任被污染考核的唯一评分者 |
| 验收AI/工具 | 运行公开/私有测试、整理证据 | 准备未污染变式 | 把私有材料放入学习上下文 |

课程设计最多领先学习者一个课程包。提前过多会依据假设生产大量无效内容。

## 11. 等待时间的并行利用

安装依赖、下载模型、训练、部署或长测试运行时，可以执行预先准备的低切换任务：

- 复习卡和错题回归
- 阅读当前功能相关文档
- 完善README和架构图
- 整理失败样本
- 写测试用例或验收清单
- 进行短算法练习

不要在等待十几分钟时开启新的复杂技术主题。切换前先保存上下文：提交或暂存代码、记录当前状态、下一步和已知错误。

## 12. 并行失控信号

出现任一组合时，降级为“仅主线＋复习”：

- 活跃任务不断增加，完成任务减少
- 主项目连续没有端到端增量
- 每天都切换多个框架或语言
- 笔记和课程进度增加，但独立考核下降
- AI辅助等级上升，核心代码等待解释或重写
- 经常忘记上次停在哪里

恢复条件：主功能完成、阻塞清零、A3/A4债务处理，并通过一个未污染的独立变式。

## 13. 并行效果评估

并行执行只有同时满足以下条件才算有效：

- 主线交付速度没有下降
- 基础支撑能力产生了独立证据
- 上下文切换没有增加明显错误
- 未完成任务数量受控
- 学习者能说清每条流如何服务当前目标

如果并行只是让学习时长、课程数量或Git分支增加，不算优化。
