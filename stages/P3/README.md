# P3｜让别人真的用上你的AI产品

这一阶段要解决的问题很朴素：不仅你自己能调用API，一个不了解代码的人也能打开页面、完成核心操作，并在出错时知道发生了什么。

优先继续使用P2项目。给它增加最薄但完整的网页界面，形成“登录—提交资料—获得结果—再次找到结果”的闭环。前端在这里服务交付，不是新的专业方向。

## 先只做一条用户主线

明确目标用户、最重要的一个问题，以及暂时不做的功能。用React完成表单、请求、加载状态、结果展示和错误提示。

在这一条流程走通前，不做复杂页面、不换状态管理框架，也不同时增加多个AI功能。

## 处理真实使用一定会遇到的麻烦

根据项目选择文件上传、搜索、分页或流式输出中的必要部分。让错误输入、网络失败、权限不足和模型失败都能被用户看见并正确处理。

加入角色和权限边界，验证用户只能访问自己的数据。前端隐藏按钮不是权限控制，后端仍要独立检查。

## 把部署变成可以重复的事情

用Docker打包应用，在Linux环境运行，并让自动测试在提交后执行。补上配置说明、日志和基本监控。

缓存、重试、限流和后台任务只在项目确实遇到相应问题时选择加入，不为了显得“生产级”一次堆满。

## 加入一个真正服务用户的AI能力

可以选择一个很小的带引用检索，或者一个需要明确确认的工具操作。它必须嵌入核心流程，并留下失败样本、费用和响应时间，而不是另做一个演示页。

## 找一个没参与开发的人来试

只把README和访问方式交给他，观察他能否完成核心流程。不要边看边提示。把卡点变成问题单，修复其中最重要的一项。

阶段结束前，再现场完成一个没有提前排练的前后端修改，证明你理解的是整个数据流，不是某一个页面或接口。

## 可以进入下一阶段的信号

- 产品有明确用户和清楚的非目标。
- 别人可以通过页面完成核心流程。
- 应用能从干净环境重新部署。
- 权限、日志、测试和主要失败路径存在。
- 你能现场修改前后端并解释数据经过了哪些层。
- 至少一个外部使用者留下了可复查反馈。

负责人使用的任务编号、验收边界和证据映射见[阶段控制表](stage-control.md)。
