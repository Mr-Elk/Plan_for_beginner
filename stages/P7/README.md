# P7｜把这一年的能力变成工作机会

最后阶段不是再学一批新技术，而是把已经形成的能力压缩成别人可以判断的证据：一个站得住的旗舰项目、一段清楚的项目讲解、陌生任务表现，以及真实求职反馈。

## 先决定拿什么代表自己

回看目标岗位和过去阶段的证据，选择最能体现后端与AI工程能力的一个项目。列出它已经证明的能力、还影响展示的关键缺口，以及明确不再添加的功能。

不要为了作品集数量再做几个新Demo。一个经历过用户、错误、部署和迭代的项目，比多个只有正常路径的项目更有说服力。

## 把项目收敛到别人可以检查

确保在线演示、源码、自动测试和部署说明可用。补齐必要的架构图、数据流、评测、性能、费用、安全边界和已知问题。

找一个真实或代理用户使用项目，根据反馈完成一次有理由的修改；再让外部开发者或模拟面试官评审代码和设计，完成第二次评审—修改闭环。

## 练习在压力下提取已有能力

混合练习Python、SQL、HTTP、测试、调试和代表性算法，不按刚学过的章节顺序出题。完成一个目标岗位风格的陌生后端任务，并保留原始过程。

准备30分钟项目答辩：讲清用户问题、架构选择、最难的Bug、AI失败、安全与成本、做过的取舍和下一步改进。遇到追问时可以修正答案，不需要背标准话术。

## 让材料服务证据

简历、README、作品集页面和演示视频只引用真实完成的内容。每条重要描述都应该能指向代码、测试、部署、评测或反馈，不能用“精通”“高性能”替代证据。

## 用真实投递结束闭门训练

选择一批方向一致的岗位进行试投递，记录反馈属于技术缺口、项目表达、简历筛选还是岗位不匹配。只针对最明确的一个缺口补强并复测，不因为单个岗位临时重学整套技术栈。

完成不等于一定拿到Offer，但应该能够证明：你可以独立交付后端优先的AI应用，能够解释和修复失败，也知道下一步怎样根据市场反馈继续成长。

负责人使用的任务编号、验收边界和证据映射见[阶段控制表](stage-control.md)。
