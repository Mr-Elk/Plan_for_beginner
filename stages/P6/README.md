# P6｜把“能跑”升级成“出问题也能管”

现在不再新开一个项目。选择P3或P5里最有价值的系统，先承认它当前有哪些问题，再把它改造成更可靠的版本。

这一阶段常见的失败不是代码完全不能运行，而是偶尔超时、模型费用失控、回答质量变化、权限放得太宽，或者出了问题却不知道一次请求经历了什么。

## 优化前先留下原始成绩

固定当前代码版本和一批代表性任务，记录回答质量、人工检查、响应时间、Token和费用。列出已经见过的失败，以及最担心但尚未验证的风险。

没有这份基线，就不能证明后面的修改真的有效。

## 让一次请求可以被追踪

加入结构化日志和调用链追踪，让你能从一个请求找到模型调用、检索结果、工具参数、耗时和错误。指标只收集会影响决定的部分，不为仪表盘好看而堆数字。

## 为常见故障准备退路

根据真实风险加入超时、重试、回退、缓存和费用上限。故意让模型接口变慢、失败或返回异常内容，观察系统是否按预期降级。

每一种恢复措施都要有测试。重试不是越多越好，缓存也不能让错误结果永久存在。

## 收紧AI能够看到和做到的事情

检查提示注入、敏感数据、用户之间的数据隔离和工具权限。工具参数必须校验，高风险操作需要人工确认，并留下可审计记录。

再模拟一次模型供应商或关键依赖变化，确认核心业务没有和某个接口死死绑在一起。

## 用一次受控对比结束阶段

选一个明确问题，例如降低超时率、减少费用或提高固定样本上的正确性。写下假设，修改一个主要变量，对比前后结果，并主动寻找反例。

最后请外部开发者做一次架构、安全或故障评审，再完成一次故障演练。你要能诚实说明系统保证了什么、仍然不能保证什么。

负责人使用的任务编号、验收边界和证据映射见[阶段控制表](stage-control.md)。
