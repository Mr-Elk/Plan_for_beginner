# P2｜把Python工具变成可以调用的服务

到这里，程序不再只从自己的终端接收命令。你要把P1的核心能力放到一个Web API后面，让别的程序可以通过网络使用它，并让数据、用户和权限都有明确归属。

最省力的做法是继续改造P1项目。例如，把“学习资料整理器”变成一个服务：用户可以注册、保存资料、搜索自己的内容，并请求AI生成标签或摘要。

## 先画清一次请求的路

从一个用户动作开始，例如“保存一条资料”。先写下请求里有什么、服务器要检查什么、数据存到哪里、成功返回什么、失败又返回什么。

然后用FastAPI做出第一个接口。此时只需要理解HTTP方法、状态码、JSON和输入校验，不要急着把所有功能都搬过来。

## 让数据真正进入数据库

为用户和资料设计表结构，用SQL亲手完成几次查询，再让接口连接PostgreSQL。你需要看懂一次请求怎样经过路由、业务逻辑和数据库，而不是只会调用ORM方法。

随后加入迁移、索引和事务。它们都应该对应一个实际问题：表结构要变化、查询变慢，或者一组操作不能只成功一半。

## 再补用户、权限和失败路径

加入登录和最小权限控制，确保一个用户不能读到另一个用户的数据。为错误输入、未登录、重复数据和数据库失败补上测试。

这部分做完后，项目才从“几个接口”变成一条可信的数据链。

## 把AI放在清楚的边界里

将模型调用封装成独立服务，固定输入输出，并记录代表性失败、响应时间和费用。先使用少量固定样本检查效果，不在这个阶段展开复杂RAG或Agent框架。

## 放到Linux上，让别人评审一次

至少部署一条完整流程到云服务器。故意制造一次配置、HTTP或数据库故障，自己定位并补回归测试。

最后通过Issue或PR接收一次真实评审：能够解释为什么接受某条建议，也允许在有依据时拒绝。

## 这一阶段真正要会的

- 能从用户流程设计接口和数据表，而不是从框架示例倒推需求。
- 能解释HTTP请求、Python业务逻辑和数据库之间的数据流。
- 能写常见SQL，并说明索引和事务解决什么问题。
- 能处理认证、输入校验、权限和集成测试。
- 遇到接口或数据库错误时，知道从日志、请求和数据哪一层开始找。

界面在这一阶段只需要能帮助调用接口，不用提前学习完整前端工程。

负责人使用的任务编号、验收边界和证据映射见[阶段控制表](stage-control.md)。
